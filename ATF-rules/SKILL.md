# Основные правила работы с кодом в нашем репозитории
## Правила работы с репозиторием:
1. Запрещается изменять/исправлять то, что не используется в созданном тесте
2. Ко всем правкам уже существующего кода относиться аккуратно, смотреть на то, где он используется и как
3. Исправлять существующие тесты - запрещено. Разрешается выводить warn по улучшению кода, но не более
4. Запрещено писать новый код, который не используется ради теста

## Правила работы с кодом:
1. Переиспользовать Fixtures
2. Не генерировать бесполезные НЕ базовые компоненты-клоны, например пустой компонент class Button {} в mui/material - это норма, так как он базовый. Но нельзя наследоваться от Button, если потомок будет пустой. Используй Button

## Правила работы с тестом:
1. Не писать комментарии шагов в самом test'e
2. В подготовке генерировать тестовые данные через fixtures. Например, не нужно регистрироваться через ui, если есть регистрация и генерация пользователя через api.
3. Запрещается записывать хоть какие либо данные в тесте, всё должно быть через fixtures
4. Запрещается использовать page в самом тесте, если нужно что-то сделать через страницу - делать это в классе необходимой страницы.
5. Запрещается проверять текстовые константы страницы в самом тесте, вся реализация таких проверок или действий - должна быть внутри страницы/компонентов

## Правила работы с Fixtures:
1. Учитывай факт: Для Fixtures переопределён контекст для request, т.к. backend работает на другом порту, поэтому подкидывать куки не получится.
2. Fixtures делится на pages - страницы ui/helpers - вспомогательные методы для генерации данных или подготовки/api - api wrapper для работы с backend


## Дополнение к промпту: правила стилистики ATF (e2e-ai-engine)

Все нижеперечисленные правила выведены из фактического кода ATF (`src/**`). Они обязательны и имеют приоритет над любыми обобщёнными практикам Playwright/POM. Отступление от правил = ошибка.

## Правила написания компонентов

### Размещение и именование файлов

1. Компоненты раскладываются по каталогам библиотек UI: `src/ui/<library>/<group>/<ComponentName>.ts`.
   - Пример фактической структуры: `src/ui/mui/material/Button.ts`, `src/ui/mui/material/TextField.ts`.
2. Имя файла строго совпадает с именем класса: `Button.ts` → `class Button`.
3. Один файл — один компонент. Вспомогательные типы выносятся в `src/ui/base/types.ts`.
4. Контейнеры и формы в специальные каталоги (найдёшь их при сканировании репозитория)

### Структура класса

4. Каждый компонент наследуется от `BaseComponentAI`:

   ```typescript
   import { BaseComponentAI } from '../../base';

   class Button extends BaseComponentAI {}

   export default Button;
   ```

5. Импорт базового класса — только именованный из barrel-файла `../base` (никогда напрямую из `./BaseComponentAI`), глубина относительного пути соответствует вложенности (`../../base` для `mui/material`).
6. Экспорт — только `export default <ClassName>;` в конце файла. Класс объявляется без ключевого слова `export`.
7. Конструктор не объявляется, если не добавляется новая логика — используется унаследованный `constructor(page: Page, dataCodeAI: string)`.
8. Если компонент не расширяет поведение базового класса (как `Button`), тело класса остаётся пустым: `class Button extends BaseComponentAI {}`. Не добавлять методы «на будущее».
9. Все поля класса (компоненты) также содержат комментарии в JSDoc на русском

### Контракт методов

9. Разрешено использовать и переопределять ТОЛЬКО методы базового контракта:
   - `fill(text: string)` — заполнение элемента;
   - `wait()` — ожидание появления в DOM (`attached`);
   - `shouldBeVisible()` — проверка видимости (`visible`);
   - `shouldContainText(text: string, options?: ShouldContainTextOptions)` — проверка текста.

### Стиль кода

1.  Каждый класс, публичный метод, поля обязаны иметь JSDoc (в компонентах — на русском языке) с `@param` для каждого параметра и `@returns`, если что-то возвращает
2.  Поиск элемента — только через унаследованный `locator()`, который строит селектор `[data-ai="<dataCodeAI>"]`. Никаких `getByRole`, `getByText`, CSS-классов, xpath и иных селекторов.

### Barrel-файл

16. Каждый каталог компонентов имеет `index.ts` с реэкспортом всех компонентов:

    ```typescript
    import Button from './Button';
    import TextField from './TextField';

    export { Button, TextField };
    ```

    Новый компонент сразу добавляется в barrel-файл своего каталога.

## Правила написания страниц

### Размещение и именование

1. Страницы раскладываются в `src/ui/pages/<PageName>Page.ts` (суффикс `Page` обязателен: `SignUpPage.ts`).
2. `import { Page } from '@playwright/test';` — тип страницы берётся из Playwright, а не из базовых классов.
3. Базовый класс и компоненты импортируются только через barrel-файлы:
   ```typescript
   import { BasePage } from '../base';
   import { Button, TextField } from '../mui/material';
   ```
4. Экспорт — `export default class SignUpPage extends BasePage`. Наследование от `BasePage` обязательно.

### Поля страницы

5. Все элементы страницы объявляются как `readonly` поля-экземпляры компонентов и инициализируются в конструкторе:

   ```typescript
   readonly firstNameField: TextField;
   readonly signUpButton: Button;

   constructor(page: Page) {
     super(page);
     this.firstNameField = new TextField(page, 'firstname-input');
     this.signUpButton = new Button(page, 'signup-button');
   }
   ```

6. Именование полей — строгий camelCase, осмысленное, с суффиксом по типу: текстовые поля — `<name>Field`, кнопки — `<name>Button` (`firstNameField`, `signUpButton`). Никаких snake_case и flatcase.
7. Конструктор страницы: первой строкой `super(page);`, далее инициализация всех полей по порядку следования элементов на форме. Ссылка на `page` дальше в коде страницы не используется.
8. Значение `data-ai` передаётся вторым аргументом и записывается строкой в kebab-case: `'firstname-input'`, `'confirm-password-input'`, `'signup-button'`. Значение берётся из вывода скрипта сканирования страницы; выдумывать коды при наличии реальных данных запрещено.

### Методы страницы

9. Страница не содержит локаторов и вызовов `page.*` напрямую — любое взаимодействие идёт ТОЛЬКО через поля-компоненты и их контрактные методы.
10. Методы-действия именуются `fill<FieldName>` (по одному на поле) и делегируют компоненту:
    ```typescript
    async fillFirstName(value: string): Promise<this> {
      await this.firstNameField.fill(value);
      return this;
    }
    ```
11. Методы-проверки именуются с префикса `should`:
    - `should<FieldName>BeVisible(): Promise<this>` → `await this.<field>.shouldBeVisible();`
    - `should<FieldName>HaveText(text: string): Promise<this>` → `await this.<field>.shouldContainText(text, { exact: true });`
12. Каждый публичный метод снабжается кратким JSDoc-комментарием (в страницах — однострочным, на русском языке: `/** Заполнить поле Username */`).
13. Один метод = одно действие/одна проверка. Комбинировать несвязанные проверки и действия в один метод запрещено.

### Работа с контрактом

15. Не обращаться к `protected`/`private` членам компонентов (`locator()`, `dataCodeAI`, `page`) из кода страницы.

## Правила написания форм

### Aggregate-метод формы

1. Форма на странице описывается одним aggregate-методом вида `fill<FormName>Form(...)`, который последовательно делегирует отдельным `fill<FieldName>`-методам:
   ```typescript
   public async fillForm(params: { username?: string; password?: string }): Promise<void> {
    if (params.username) {
      await this.fillUsername(params.username);
    }
    if (params.password) {
      await this.fillPassword(params.password);
    }
  }
   ```
2. Параметры передаются строго позиционно, в порядке следования полей на форме (визуальном порядке сверху вниз), имена — camelCase, отражают смысл поля, а не `data-ai` дословно.

### Именование

5. Имя метода строится от названия формы/страницы: `fillSignUpForm`, `fillLoginForm`, `fillCheckoutForm`. Один aggregate-метод на одну логическую форму.

### Ограничения контракта и предупреждения

6. Заполнение и сабмит не смешиваются: aggregate-метод отвечает только за заполнение (префикс `fill`). Отдельные действия сабмита выносятся в самостоятельные методы — если контракт компонента это позволяет.
7. Если сабмит невозможен из-за отсутствия метода в контракте компонента (например, у `Button` нет `click`):
   - аккуратно сгенерировать отсутствующие методы. Думать над тем, где генерировать, возможно метод можно использовать в наследуемых компонентах. Обязательно следовать SOLID;
   - вывести в лог warning

### Проверки формы

8. Проверки полей формы не входят в aggregate-метод заполнения — они реализуются отдельными `should...`-методами страницы и вызываются из теста независимо (принцип: действие отдельно, проверка отдельно).
9. Минимальный набор проверок формы, доступный по контракту без расширений: видимость каждого поля (`should<FieldName>BeVisible`) и видимость кнопки сабмита (`should<Name>ButtonBeVisible`).

# Fixtures

Обязательно проанализируй fixtures у ATF и используй их при необходимости. Также тебе разрешается их дополнять. Все тестовые данные генерируется в fixtures. Некоторые данные могут быть статичны. Так их в фикстурах и можно написать. Но не должно быть объявлений новых данных в самом тесте.

## Api Fixtures
Api работает в другом контексте, так как бэкенд на другом порту (3001). Из-за этого может не получиться залогиниться, например. Думай сам как правильно решить эту задачу.

# Проверка

После генерации и сохранения тесты - ты обязан запустить его и проверить, что он отработал. Если он отработал не успешно - попытаться починить 1 раз, если неуспешно, то вывести ошибку и закончить работу.

# Типизация

Типы всегда должны описываться в отдельном файле types.ts в том каталоге, ради чего они и описываются.
